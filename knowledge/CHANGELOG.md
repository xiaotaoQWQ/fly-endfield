## 2026-10-29 · 逐帧对比验证：ONNX 全对，旧模板 5 次误报

**为什么**：接入 ONNX 后必须证明它**确实更好**，而不是"能跑就行"。

**怎么验**：428 帧同一帧跑两套识别 + **把分歧帧裁出来亲眼看**
（`_cmp_combo.py` / `_cmp_show.py` → `shots/combo_dispute.png`）

**结论**：

| | 旧模板 | ONNX |
|---|---|---|
| 触发帧数 | 7 / 428 | 2 / 428 |
| 真提示（人工核验） | 2 | 2 |
| **误报** | **5**（corr 0.514~0.645，全在边缘） | **0** |

误报的 5 帧框里是**纯背景**或**Windows 桌面**，根本没有 E 徽标。

**这解释了历史上的连携技 bug**：
模板在 0.51~0.65 的边缘值上乱触发 → "连按 11 次"。

**坑**：
1. **"一致率 98.8%" 是骗人的** —— 428 帧只有 2 帧真提示，
   "全说没有"就有 99.5% 准确率。类别极端不平衡时，
   准确率完全不能评价判据；要看**误报率** + **人工核验分歧帧**。
2. 第一次对比时模板相关值最高只有 0.346 ——
   模板是 2560 尺度的 30×28，但喂的是 1280 裁图（大了一倍）。
   **模板尺度必须和搜索区一致。**

## 2026-10-29 · 接入 MaaEnd 的 ONNX 识别（替代连携技模板检测）

**为什么**：连携技识别用模板/颜色做了三版，都在录像上零误报、实机上车翻
（§40 抓错 UI 元素、§46–51 三版判据）。MaaEnd 训了一个 YOLO11s，
一次推理给出 22 类战斗 UI 的框+标签+置信度，比我们手抠的模板稳得多。

**改哪**：
- 新增 `onnx_detect.py`（约 380 行，含自检 13 条）
- 新增 `download_model.py`（下载 + 校验 37,960,805 B）
- 新增 `requirements.txt`
- `endfield_fly.py`：`--onnx/--no-onnx/--onnx-conf/--onnx-model`；
  主循环每拍跑一次 ONNX；**连携技判断优先用 `combo_active`**；
  状态 HTML 加 7 个 ONNX 字段
- `build_exe.py`：`DATA_DIRS` 加 `("models","models")`

**怎么验**：
```bash
python -X utf8 download_model.py          # 下载 36.2 MB（约 10 分钟）
python -X utf8 onnx_detect.py             # 自检 13 条
```
启动日志应出现：`★ ONNX 识别已启用（替代连携技模板检测）`

真实帧验证（428 帧录制）：
```
0022: 18框 ★连携 大招 连携4/4   active=True  hp=4n end=True e=2
0040: 15框 ★连携 连携3/4        active=True  hp=4n end=False
0048:  2框                      active=False hp=0n   ← 战斗结束
```
速度：中位 96 ms（2.5 Hz 预算 400 ms）。

**坑**：
1. **代码顺序**：ONNX 块第一版插到了连携技判断后面 → `UnboundLocalError`。
   插代码要看**依赖方向**，不能只看锚点就近。
2. **变量作用域**：用了后面才绑定的 `fod` → 改用 `forager`。
3. **下载截断**：36 MB 约 60 KB/s，`--max-time 600` 会截断成 29 MB；
   必须 `--max-time 900` + **校验字节数 37,960,805**。
4. `raw.githubusercontent.com` 不通 → 用
   `api.github.com/repos/.../contents/...` + `Accept: application/vnd.github.raw`。

## 2026-10-28 · 调研 MaaEnd / MaaFramework —— 结论：不能整体换

**为什么**：用户提出「把识别换成 maaend，这个识别比自己做的屏幕抓取要好」。

**结论（三条，都有实测）**：

1. **A 方案（整体集成）不可行** —— maafw 5.14.3 没有 cp314 wheel，
   我们的 Python 3.14.7 装不上。而且它是任务流水线框架，
   不是「给个模板返回相关值」的库，架构和我们的 2.5 Hz 同步循环不匹配。

2. **B 方案（OCR 判状态）方向错** —— 试了 Windows 自带 OCR（系统里有 zh-Hans-CN）：
   4/5 时好时坏，中文全糊。**而且 MaaEnd 自己也不用 OCR 判状态** ——
   它的 OCR 只用于读干员等级/名称，状态判断全走 ColorMatch。

3. **C 方案（借它的模板/参数）只能借思路** —— 拿它调好的
   ComboUsable / HasEnemy 在我们的 428 帧上跑：
   一个 8 帧只命中 1 帧，一个全部为 0。它的 ROI 绑定它自己的
   分辨率/UI 缩放/游戏版本，搬不过来。

**真正的收获（可以借）**：
- ★ 用**最大连通域面积**代替**颜色占比** —— 天然抗零散同色噪点
- 连携技改判「一条细白条」而不是「E 徽标模板」—— 更简单、不用管分辨率
- 模板匹配加 green_mask —— 只匹配形状不匹配颜色，抗背景变色

**改哪**：新增 knowledge/07-MaaEnd调研.md；_maa_probe/ 留了它的
Recognition.json（9809 B，调好的 ROI + 颜色区间，值得逐条读）

**怎么验**：见 07 篇的双表（工具对比 + 我们的 428 帧实测）

**坑**：
aw.githubusercontent.com 在这台机器上不通 ✗ ——
拉 GitHub 文件要用 pi.github.com/repos/.../contents/...（base64）✓

## 2026-10-09 · 饥饿值：清空 + 10 秒不涨 + 之后恢复

**为什么**：原来是「永久冻结」（带着当前饱腹度停住）。
用户更正：应当是**清空** + **10 秒不涨** + **之后恢复正常**。
语义上也更对 —— 打赢一局 = 吃了一顿；哪有一顿饭管一辈子的。

**改哪**：`mb_learn.Hunger.clear(hold_sec)` + `step()` 里的倒计时

**怎么验**：
```python
h = Hunger(h0=0.85, rise=0.05)
h.clear(10.0)          # h -> 0
# 9.5 秒后仍是 0；11 秒后开始涨
```

**坑**：用**倒计时**不用时间戳 —— `step()` 只拿到 `dt`，拿不到绝对时间。
用墙钟的话，果蝇暂停 5 分钟再恢复，那 10 秒窗口就被"跳过"了。

## 2026-10-09 · 修鼠标滚轮静默改键位

**为什么**：用户报「为什么会按 q」。日志显示 `combo_key` 被改成了 `q` ——
`ttk.Combobox` **悬停时会被鼠标滚轮改值**，用户一边玩游戏一边滚滚轮，
鼠标扫过面板就把键位改掉了。于是按错键 → 连携技提示不消失 →
检测器一直为真 → **每拍都按** → 7 秒连按 11 次。

**改哪**：`app_window.py` 下拉框 `bind("<MouseWheel>", "break")`；
面板常驻一行「键位」；`endfield_fly.py` 连按 4 次就警告

**怎么验**：面板最上面能看到当前键位；故意把 `combo_key` 设错时，
日志 4 次后出现 `⚠ 连携技连按 4 次（键「x」）提示仍不消失`

**坑**：先做了排除 —— 建窗口时**一行 `[键位]` 都没有**，
说明不是"初始化时自己触发"，而是真实的鼠标操作。
**先分清是"代码错"还是"用户操作"，再动手修。**

## 2026-10-09 · 按键/技能含义可配 + 清空记忆

**为什么**：技能语义原来写死成「1 伤害高 · 2 挂削弱 · 3 增伤 · 4 回血」，
换配队就全错。而且错得很隐蔽（照常按键、照常打，只是打在错的地方）。

**改哪**：
- `--role-1..4`（attack/buff/block/heal/gather/weaken/none）
- `--key-skill1..4`
- `--key-ult`（逗号分隔的键序列）
- `mb_learn.innate_priority(roles=...)`
- `MushroomBodyLearner.reset()` + 面板「清空记忆」

**怎么验**：
```
攻/增/挡/回 血60%  [1.00 0.00 1.55 0.00] -> 3   格挡
攻/增/挡/回 血30%  [1.00 0.00 0.00 2.20] -> 4   回血
聚怪/攻击/无/无 开战 [1.55 1.00 0.00 0.00] -> 1   聚怪
全 none（事故配置）  [0.00 0.00 0.00 0.00] -> 1   兜底不空转
```

**坑**：下拉框存的必须是**值**不是**显示文字**。
写显示文字的话 argparse 收到的是中文长句 ——
**表面上不报错，但语义全丢**。

## 2026-10-09 · 连携技标定重做（原来抓错了 UI 元素）

**为什么**：用户报「特定角色 E 不释放」。录屏 951 帧离线回放，
发现旧模板的最高相关只有 **+0.460**，而 `>=0.45` 只有 **2/951 帧** ——
**99.8% 的时间里它根本看不见提示**。把帧里的 E 徽标和旧模板并排一比：
抓的是**队友圆形头像上的另一个徽标**，完全不同的 UI 元素。

**改哪**：
- `templates/combo_e.npy` 换成真 E 徽标（**30×28**，内容尺度）
- `ComboMarker.step()` 不再降采样
- `REGIONS["combo"] = (1400, 590) 200×100`（收紧）
- 阈值 0.60 → **0.50**（8 种分辨率实测）

**怎么验**：951 帧回放，旧标定 **2/951** 命中，新标定 **115/951**，
真提示 +0.75~+1.00、噪声底 +0.333。

**坑**：标定必须**离线回放验证全部帧看分布**，
不能只看"当时抓到了"。当初只测了"真提示 +0.606、假的最大 +0.267"就收工，
那组数字**只对当时那个场面成立**。

## 2026-10-09 · 整帧抓取（LiveFrame）+ 多分辨率验证

**为什么**：改之前每拍抓 **7 次**屏幕，两次之间隔十几毫秒，
而游戏是 60 fps 在跑的 —— "血条还剩 30%"和"红环亮着"
**可能不是同一时刻的状态**。

**改哪**：新建 `live_frame.py`；主循环所有 HUD 改成从同一帧切片

**怎么验**：整屏 87 ms vs 7 个区域 105 ms —— **更一致，还略快**；
8 种分辨率召回率 97%~100%（阈值 0.50）

**坑**：眼睛线程**不走**这条路 —— 它要 30 Hz，而整屏抓一次 87 ms
（最多 11 Hz）不够。**眼睛要快，HUD 要准**，两个需求本来就冲突。

## 2026-10-09 · 对照组（消融实验）

**为什么**：项目的两条底线里，第一条是"它得真的在控制那个角色"。
**光靠嘴说没用 —— 得能把某个脑区关掉，看行为变不变。**

**改哪**：`live_tune.TOGGLES`（7 个开关）+ 面板复选框；
`endfield_fly.py` 各处的 `args.ab_*` 判断

**怎么验**：全关时 `饥饿值 h` 锁在 0.500；关掉「连接组」后
神经网络输出变成固定种子的随机数，行为明显变乱

**坑**：「运动输出关掉」是在执行器外包一层空操作，
第一版拦的是 `("apply","press","hold","click")` ——
**漏了 `combat_press` 和 `combat_hold_down`**，那才是打怪真正用的通道。
**「关掉某个功能」要实现成「单一闸门」，不是「在每个出口加判断」。**
