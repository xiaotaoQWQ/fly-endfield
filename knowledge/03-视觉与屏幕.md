# 03 · 视觉与屏幕

> 它怎么"看见"游戏，以及为什么这块最容易翻车。

---

## 一、★ 第一原则：抓的是**屏幕**，不是窗口

```python
# ef_shot.py
grab(x, y, w, h) -> np.ndarray   # GDI BitBlt 从屏幕 DC 抓
```

**`PrintWindow(hwnd, PW_RENDERFULLCONTENT)` 对这个 DirectX 游戏返回 0 / 全黑。**
试过，拿不到。

**后果**：任何压在游戏上面的窗口，都会被当成"游戏画面"读进去 ——
**不报错、不崩溃、只是那个功能永远不触发**。

实测踩过的三个症状，根因是同一个：

| 被挡的区域 | 症状 |
|---|---|
| 连携技搜索区 | E 键永远检测不到 → 永远不放连携技 |
| 血条 | 血量读不到 → 自动挨打失效、大招永远不放 |
| 任务完成横幅 | 打完副本不给奖励 |

**对策**：`screen_profile.check_occlusion()` 启动时检查，
`WindowFromPoint` 看每个区域中心点的最上层窗口是不是游戏自己。

## 二、整帧对象（LiveFrame）

```python
lf = LiveFrame(prof, grab)
lf.update()                        # 每拍抓一次
lf.at(x, y, w, h)                  # 按内容坐标切片
lf.region("hp")                    # 按标定名切片
lf.find(tpl, sub)                  # 在切片里找模板 → (corr, x, y)
```

**为什么要它**：
- 改之前每拍抓 7 次，两次之间隔十几毫秒 —— 而游戏是 60 fps 在跑的
- **"血条还剩 30%"和"红环亮着"可能不是同一时刻的状态**
- 实测：整屏 87 ms vs 7 个区域 105 ms → **更一致，还略快**

**越界自动裁剪，不抛异常**：标定值在别的分辨率下换算出界是常事，
抛异常会让整只果蝇停摆，少几个像素无所谓。

**`find()` 也要防零方差**：平坦区域（纯色 / 黑屏 / 对话框白底）
会让 `std(x)≈0` → 分母被 `1e-6` 兜住 → **相关值爆炸到 7 亿** → 判定为"匹配"。

```python
den = np.sqrt(var) * tn
sc = np.where(den > 1e-3, num / np.maximum(den, 1e-6), 0.0)
```

## 三、各个检测器

### 3.1 红环（战斗中）

| | |
|---|---|
| 区域 | 内容 `(28, 47) 48×50` |
| 判据 | 红色像素数 `--marker-min-px`（默认 80）|
| 用途 | `m_red` → 战斗中 = `m_evac or m_red` |

### 3.2 撤离面板（副本内）

| | |
|---|---|
| 区域 | 内容 `(24, 45) 213×53` |
| 判据 | 模板 `evac_panel` 相关 > `--evac-corr`（0.55）|
| 用途 | `m_evac` → 副本内 = 可以随时出手 |

**为什么用它当闸门而不是红环**：红环要打起来才亮，
而撤离按钮**进副本就有**。

### 3.3 连携技徽标（E 键）

| | |
|---|---|
| 区域 | 内容 `(1400, 590) 200×100` |
| 模板 | `combo_e.npy` **30×28**（圆角方块 + 白色 E）|
| 判据 | 相关 > `--combo-corr`（0.50）|
| 冷却 | `--combo-cool`（默认 **0**，无冷却）|

**★ 这一块标定重做过三次，是踩坑最多的**：

- **第一版抓错了 UI 元素**：抓到的是**队友圆形头像上的徽标**，
  不是 E 键提示。表现是"特定角色 E 不释放"。
- **降采样是错的**：`step()` 里 `a[::2, ::2]` 会把 30×28 变成 15×14，太小了。
- **搜索区不能太大**：`(1240,400) 700×560` 的噪声底高到 0.437，
  `>=0.45` 有 **75/172 帧**——一半的帧都会误判。

**实测（951 帧 × 8 种分辨率）**：

| 分辨率 | 模板 | 阈值 0.60 召回 | **阈值 0.50 召回** | 噪声底 |
|---|---|---:|---:|---|
| 2560×1440 | 30×28 | 100.0% | **100.0%** | +0.335 |
| 1920×1080 | 22×21 | 93.0% | **99.1%** | +0.354 |
| 3840×2160 | 45×42 | 95.7% | **99.1%** | +0.339 |
| 1600×900 | 19×18 | 84.3% | **99.1%** | +0.360 |
| 1280×720 | 15×14 | **74.8%** ✗ | **97.4%** | +0.400 |
| 2560×1080 | 30×21 | 97.4% | **99.1%** | +0.344 |
| 1920×1200 | 22×23 | 96.5% | **99.1%** | +0.354 |
| 1680×1050 | 20×20 | 87.8% | **99.1%** | +0.359 |

**规律**：模板越小 → 重采样越糊 → 真信号越低、噪声底越高。
所以阈值取 **0.50**，每种分辨率召回都是 97~99%。

**独立交叉验证**（不依赖标签的判据）：统计"判定有提示"的帧占比。
真值 12.6%，八种分辨率都是 **12.3%~12.8%** → **没有额外误报**。

### 3.3b 连携菱形（环上方那枚 ⟡）—— ★ 认得出祀

| | |
|---|---|
| 区域 | 内容 `(1490, 500) 140×130` |
| 模板 | `combo_diamond.npy` **32×22**（内容尺度；源文件 16×11@1280，MaaEnd 的 `AutoFight/Combo.png`，AGPL-3.0）|
| 判据 | 相关 > `--combo-diamond-corr`（默认 **0.80**）|
| 防抖 | `--combo-vote`（默认 1 = 不防抖；3 = 最近 3 拍过半）|

**为什么要有这一路**：ONNX 模型认不出新角色「祀」的提示（`combo_raw` 恒 0）。
提示圆环**正上方那枚小白菱形**跟角色无关 —— MaaEnd 的资源里正好留着它的模板。
两路**取或**：`m_combo = ONNX(combo_active) or 菱形`。

**实测（1515 帧 + 祀那张 2560 截图）**：

| 数据 | 帧数 | 真提示 | 负样本最高 |
|---|---:|---|---:|
| 20261009_173122 | 428 | 0.988 / 0.967（就是人工核验的 0022 / 0040）| **0.490** |
| 20261008_002304 | 136 | 0.938 ~ 0.985 | 0.532 |
| 20261008_002642 | 951 | 0.95 ~ 0.99（抽查 3 帧全是真提示）| **0.682**（白屏 / 资源管理器）|
| **祀（2560）** | 1 | **0.952** ✓ | — |

**判据怎么定的**：0.80 是 MaaEnd 自己用的值。真提示最低 0.94、负样本最高 0.68
→ 空档 0.12；0.85 更保守（空档 0.17），但 0.80 更不容易漏 —— 而「没提示时按 E
在终末地没有副作用」，所以宁可多按。

**坑**：这枚模板是**连续多帧为真**的信号（951 帧那份 119 帧命中、最长连续 13 帧），
所以外层必须靠**上升沿**触发；想更稳再加 `--combo-vote 3`。

**复现**：`python -X utf8 check_combo_diamond.py`（验收条件写在脚本里，退出码 0 = 通过）

## 四、★ 标定方法论（下次别再返工）

### 4.1 必须用**真实录像**离线回放验证

**不是**"当时抓到了"，而是"在一整段真实录像上，
信号和噪声之间有一条清晰的沟"。

```
1. 录屏（rec_combo.py，只存变化帧，原生像素）
2. 离线把所有帧跑一遍检测器
3. 看分数的**分布**：中位数 = 噪声底，最高值 = 真信号
4. 确认两者之间有清晰分离
```

### 4.2 区域、阈值、时间**三个参数要一起标定**

分开调会互相拆台。区域越大噪声底越高，阈值就得跟着抬，
然后召回就掉。

### 4.3 一定要测**反向样本**

想清楚"还有什么东西长得像它"，然后**专门造那个**测一遍。

例：连携技徽标 → 金色伤害数字；任务条金带 → 拾取高亮。

### 4.4 ★ 算噪声上界前，先确认"真值集合"是完整的

**踩过**：算"其余帧最高相关"得到 4.618%，以为噪声很大。
其实那是**第二帧真完成帧**——录制里完成状态持续了两帧，我只排除了第一帧。

**后果**：为了躲开"噪声"把阈值抬到一个错的高度。

### 4.5 判据要和信号的**性质**匹配

| 信号是什么 | 该用什么 |
|---|---|
| 色块 | **颜色占比**（成本低一个数量级）|
| 文字 / 任意形状 | **模板匹配**（归一化相关是相对的，背景变化不影响）|
| 某个东西"在不在" | 模板匹配 + **消失持续时间** |
| 某个东西"变了" | 差分 / 亮度 |

**我在第 46 篇写过"能用颜色判的就别上模板"——那句话对色块成立，对文字不成立。**
颜色判据对**区域**极其敏感（区域里多一样同色东西就完了），
模板匹配对区域不敏感（它在区域里找形状）。

### 4.6 颜色判据的"区域"和"阈值"是一对

用颜色判据时：
1. **区域要切到目标本身**（先逐行定位金色像素在哪，别偷懒用一大块）
2. **至少两个正交条件**（占比 + 形状），别只数面积
3. **标定时想清楚"还有什么东西长得像它"**，然后专门测那个

## 五、眼睛（复眼感光细胞）

### 5.1 主画面口径（`--eye main`，默认）

```
画面 → 降采样（--eye-ds 4）→ 乘以感光细胞方位角掩膜 → drive
```

**关键**：它**不需要 heading**。第一人称画面本身就是自我中心的，
感光细胞的方位角直接对应画面的横向位置。

heading 仍由小地图里程计提供（面板显示 + 撞墙判定用）。

### 5.2 小地图口径（`--eye minimap`，旧）

```
小地图 → 环采样（半径带）→ 左右配对投票（sector_vote.py）→ drive
```

方位角要按 heading 旋转，所以依赖里程计。

> 小地图标定曾错位 40 px（半径的 34%）——
> 写死圆心 `(188,236)` 半径 `143`，实测应该是 `(228,208)` 半径 `118`。
> 结果把左侧 HUD 和右下角游戏世界都当成地形喂给了果蝇。

### 5.3 角色遮罩（`--eye-skip`）

第三人称相机下**角色杵在画面正中**，正好挡住 looming 最该出现的正前方。
所以中间那块要遮掉（默认 `0.41,...`）。

### 5.4 自动切换（`--eye-auto`）

对比度低于 `--eye-contrast`（0.24）→ 连续 2 拍 → 切到小地图。
回到 `--eye-back`（0.33）以上 → 连续 4 拍 → 切回主画面。
两次切换至少隔 `--eye-dwell`（20）拍。

**「失效」的定义**：画面没信息（对比度低）**或** 推不动（相机贴背）。

## 六、常见故障对照

| 症状 | 先查 |
|---|---|
| 某个功能永远不触发 | **遮挡检查**（启动时的警告）|
| 相关值是个天文数字 | 零方差没防住 |
| 相关值永远 0，不报错 | 模板比搜索区还大 → `if g.shape[0] < th: return False` |
| 换了分辨率就认不出来 | `TEMPLATES` 里的参考分辨率写错 |
| 检测到但位置不对 | 内容区测错（黑边没去干净）|
| 一半的帧都误判 | 搜索区太大，噪声底太高 |
